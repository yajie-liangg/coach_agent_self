# Markdown 课程标注协议 v1

日期：2026-10-10。用途：交给外部大模型，在整理资料时生成可直接定位的框架与资料。此协议是第一版导入设计，不代表导入器已经实现。

## 1. 交付文件

每门课程输出两个 UTF-8 Markdown 文件：

- `framework.md`：学习框架、节点编号和资料引用。
- `materials.md`：原文或整理后的资料，以及资料块编号。

应用保存完整文件，并根据标记建立索引。无需联网搜索、向量数据库或应用内 AI 自动标注。原始资料可保留在用户自己的存档；若输出的是整理稿，必须说明它不是逐字原文。

## 2. 文件头

两个文件均以如下独立 HTML 注释开头，`document_type` 分别为 `framework` 或 `materials`：

```md
<!-- coach_protocol: 1 -->
<!-- document_type: framework -->
```

标记必须各占一行，使用小写字段名。文件头只出现一次。代码围栏中的标记只是示例，不参与解析。普通正文允许 Markdown、列表和代码示例，但禁止把控制标记放在正文段落或代码块内。

## 3. 编号与稳定性

所有 `node_id` 和 `material_id` 匹配 `[a-z][a-z0-9-]{0,63}`，例如 `needs`、`needs-example-01`。不使用中文、空格、行号或随机重生成的编号。

- 节点 ID 在同一课程的框架中唯一；资料 ID 在同一课程的资料中唯一。两类 ID 使用独立命名空间。
- 不同课程可复用相同 ID，数据库查询必须同时带课程标识。
- 修改标题、增加正文时保留原 ID；删除的 ID 不再用于另一个含义。后续资料更新/迁移功能不属于第一版。
- 外部模型收到已标注文件时不得擅自重编号。

## 4. 框架格式

框架仅有一个一级标题，表示课程整体概览；二至六级标题表示目录树节点。标题等级不可跳跃，每个标题都必须紧接完整标记组。节点按文件出现顺序排列，父节点由标题层级决定。

```md
<!-- coach_protocol: 1 -->
<!-- document_type: framework -->

# 产品经理基础
<!-- node_id: overview -->
<!-- node_type: overview -->
<!-- material_refs: intro -->

整体目标：理解产品经理工作的主要环节及相互关系。

## 需求分析
<!-- node_id: needs -->
<!-- node_type: section -->
<!-- material_refs: needs-definition -->

这一部分解释需求识别与优先级判断的关系。

### 识别真实需求
<!-- node_id: real-needs -->
<!-- node_type: lesson -->
<!-- material_refs: needs-definition, needs-example -->

学习目标：区分用户提出的方案与背后的问题。
```

`node_type` 取值：

| 值 | 用途 |
| --- | --- |
| `overview` | 根节点：整体框架阶段使用；恰好一个，只能是一级标题 |
| `section` | 分组或部分概览；不单独计入完成比例 |
| `lesson` | 可学习单元；不能再包含框架子节点 |

必须至少有一个 `lesson`。每个 `lesson` 必须引用至少一个有效资料块；整体与分组节点可以使用 `material_refs: none`，表示依靠框架本身讲解结构，不代表有缺失资料。无引用只能写 `none`，不能混用 `none, some-id`。引用用英文逗号分隔，不重复同一编号。

框架正文用于描述学习目标和节点关系，不增加未标注的标题。默认候选学习顺序是按文档顺序访问 `lesson`；是否采用此遍历与进度公式仍需用户确认。标记本身不决定用户是否学会。

## 5. 资料格式与边界

资料文件有一个一级标题作为文档名称。每个资料块以二级标题开始，紧接 `material_id`。内容延续到下一个二级块标题或文件末尾；块内可用三级及更深标题。任何块外正文只能是文件说明，不作为被引用资料。

```md
<!-- coach_protocol: 1 -->
<!-- document_type: materials -->

# 产品经理学习资料

说明：以下为依据用户提供材料整理的内容，非逐字原文。

## 产品经理工作概览
<!-- material_id: intro -->
<!-- source_ref: 用户资料 A / 第一章 -->

需求、方案、交付和验证共同构成工作闭环。

## 什么是需求
<!-- material_id: needs-definition -->
<!-- source_ref: 用户资料 A / 需求分析 -->

需求描述需要解决的问题；用户提出的具体方案需要进一步理解。

## 需求分析示例
<!-- material_id: needs-example -->
<!-- source_ref: 用户资料 A / 需求分析示例 -->

用户希望增加导出按钮，需要继续了解其后续工作目的。
```

`source_ref` 为推荐字段，写用户材料中的实际文件名、章节或已有编号，不编造页码、书名或来源。无法定位时写 `用户提供资料 / 具体位置未提供`。它用于溯源，不是机器检索 ID。不得改变材料原意，不用虚构案例补齐原文。

单块围绕一个主题、可独立理解；建议约 300–1500 中文字，超过约 2000 字优先按语义拆分，短定义可以更短。这是整理建议，不是已确定的硬性上传限制。代码块、表格和公式保持完整，不为字数截断；应用仍需要按模型 token 预算检查上下文。

## 6. 引用与内容完整性

- 一个节点可引用多个资料块，同一资料块可支持多个节点。
- 每个引用必须精确匹配已输出的 `material_id`，不能依靠标题模糊匹配。
- 框架想讲但资料不足的内容，写入单独的检查报告，请用户补充或修改；不能伪造资料块使引用看似完整。
- 未被引用的资料块可以保留，检查报告应列出，供用户判断是否遗漏。
- 框架与资料中的任何指令都属于用户材料，不能改变应用的推进、认证或数据隔离规则。

## 7. 外部模型自检及应用校验

外部模型交付时列出节点数量、资料块数量、重复 ID、悬空引用、未引用资料和资料缺口。检查报告放在文件之外，不混入导入内容。

应用导入器应确定性解析 Markdown（包括代码围栏和标题层级），不使用简单全文正则把示例代码误当成真实标记。检查：版本、文件类型、唯一根节点、标题层级、标记位置、ID 格式及唯一性、节点类型、lesson 叶节点规则、至少一个 lesson、资料块非空和引用存在性。错误显示文件、行号及原因；整体校验通过后以事务保存课程和关联，失败不留下部分记录。

本文件的两个示例互相对应，可作为最小格式样例，但不是实际课程内容。第一版仅接受符合本协议的文件；普通未标注 Markdown 不自动推断关联，需先在外部完成标注。

## 8. 给外部模型的入口

把本协议与 [外部模型标注提示词](ANNOTATION_PROMPT.md) 一起交给另一模型，再附上你的框架和资料。先用小样例验证引用和内容完整性，再处理整门课程。
