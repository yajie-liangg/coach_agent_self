# 开发协作约定

## 工作依据

- 开始任务前阅读 `Docs/SDD.md`、`Docs/TDD.md` 和 `Docs/PROJECT_STRUCTURE.md`。
- 本项目采用规格驱动开发（SDD）：先讨论并确认需求，再更新规格，最后实现。当前文档是已讨论需求的整理稿，等待用户审阅；不要将待定项当成已确认需求。
- 未经需求讨论，不增加功能、不修改用户课程框架。范围变更先更新规格和验收场景。
- 当前阶段仅编写文档，不实现应用。用户确认文档并授权实现后，再进入 TDD。
- 使用已有检出目录；云任务已经隔离，除非用户明确要求，不创建 Git worktree。

## 代码设计

- 采用面向对象的方式，以功能和职责为单位封装。避免只为形式创建类、庞大的万能类和不必要的继承。
- 课程管理、材料导入、学习状态、对话编排、模型调用与持久化应有清晰边界。目录遵循 `Docs/PROJECT_STRUCTURE.md`；具体语言和框架在实现前确认。
- 对外接口明确输入、输出、错误和副作用；使用类型定义与必要的文档说明。
- 命名和执行顺序符合人类阅读逻辑。注释解释设计原因、边界及非显然行为，不重复代码本身。
- 将业务规则与模型供应商、数据库、HTTP 等基础设施分离，便于人或 AI 微调、替换和迭代。
- 模型生成文本不能直接改变框架、课程归属或学习进度。状态变化由应用规则校验并持久化。

## TDD 与验证

- 对照 `docs/TDD.md`，先写会因目标行为缺失而失败的测试，再实现最小代码，最后在测试保护下重构。
- 业务单元测试使用可控的模型替身；真实 API 验证单独执行并明确费用、联网和凭据前提。
- 优先验证课程隔离、用户控制进度、记忆恢复、材料依据和失败恢复，不写只重复实现细节的测试。
- 每次交付报告实际执行的检查，以及失败、跳过和未运行项。不得把未执行的测试说成通过。

## 数据与安全

- 不在仓库、浏览器代码、日志、文档或聊天中保存 API Key；由服务端安全配置提供。
- 不打印完整环境变量或凭据。错误信息不得暴露密钥和其他课程的内容。
- 对外部署前必须确定并实现单用户访问保护；账号展示不代表已经有认证能力。
- 只向模型发送当前课程需要的资料、对话和记忆；不进行网页搜索。
- 不自动把未经用户确认的推测写成长期个人事实。

## 文档维护

- 保持需求、接口约定、验收场景与最终实现一致。
- 区分已确认需求、技术建议和待定决策；不把建议升级为强制规格。
- 提交代码时说明变更目的、验证结果及实际限制。提交、推送或部署需要用户授权；本次用户已授权将文档及原型提交、推送至 GitHub。
